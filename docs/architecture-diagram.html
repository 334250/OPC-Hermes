核心设计原则

🔒 不修改 Hermes Agent 源码

以插件、配置注入、外部编排的方式工作。Hermes Agent 升级时 OPC-Hermes 不受影响。

🧠 记忆天生隔离

项目记忆、评估记忆、知识库三者物理/逻辑分离，评估 Agent 不污染执行 Agent 的上下文。

📊 复杂度即 Skill

复杂度判定是一个可复用、可独立进化的共享 Skill，非内嵌逻辑。

🔄 进化有据可查

每次模型切换、工具替换、Prompt 变更都经过数据驱动的提案→审批→切换流程。

集成机制详解

🔌 OPC Plugin 启动流程（零侵入集成） Plugin 驱动
1
Hermes Agent 启动
扫描 plugins/ 目录 + pip entry_points → 发现 opc_hermes 插件
2
调用 opc_hermes/plugin.py: initialize(ctx)
注册 OPC 工具：opc_save_context / opc_get_upstream_summaries / opc_write_to_bridge / opc_complexity_rate ...
3
运行时追加 TOOLSETS
TOOLSETS.update({"opc_memory": ..., "opc_leader": ..., "opc_evaluator": ...}) — Python dict 可变性，不修改源文件
4
注册 Cron 定时任务
create_job("opc_optimizer_scan", "1h") + create_job("opc_knowledge_crawl", "24h")
5
绑定 Gateway Hook
pre_gateway_dispatch hook：判断任务复杂度 → 路由到 Leader 或正常 Agent

部署架构

🖥️ 进程 1: Hermes Agent
核心 Agent 运行时
• AIAgent 核心循环
• Gateway (22 平台)
• Plugin System (含 OPC Plugin)
• Tool Registry (含 OPC 工具)
• Cron Scheduler
• Web Dashboard (端口 9119)
🌐 进程 2: OPC WebUI
独立 FastAPI 应用 (端口 9120)
• React 前端 (Vite 打包)
• RESTful API
• WebSocket 实时推送
• 直读 SQLite (WAL 模式)
• command_queue → Leader 轮询
🤖 进程 N: Worker Agents
每个 Worker = 独立 subprocess
• 标准 Hermes Agent 实例
• 独立会话 + 工具集
• 通过 TaskProtocol 接收任务
• 通过 ProgressReport 回报
• 300s tool call 硬超时
关键约束： 所有进程通过 SQLite WAL 模式共享数据文件（读写不互斥）。 OPC WebUI 完全不依赖 Hermes 9119 端口，零耦合。 Tool call 硬超时 300 秒，Worker 执行必须拆分为多步调用。
